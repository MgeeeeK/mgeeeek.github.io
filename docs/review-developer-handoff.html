2. Framer migration — what's actually there

branch matte-drift, live preview checked directly
Blocked

The contact form is entirely fake — it does not capture any input

I inspected the DOM directly: document.querySelectorAll('input, textarea') returns zero elements, and document.querySelectorAll('form') returns zero. The Name/Company/Email-id/Message boxes are static text styled to look like inputs. "Send" is a hardcoded <a href="mailto:abhiv1999@gmail.com"> with no subject or body — whatever a visitor types is never captured or sent anywhere. This is a regression from the Next.js version, which at least builds a real (if unvalidated) mailto body from real form fields.

This needs Framer Forms wired up from scratch, or a real code-component form. It was never built — this isn't a bug to patch, it's a missing feature.

Blocked

The homepage headline visibly reads "Abhi' Portfolio" — the "s" is missing on screen

Confirmed reproducible across multiple fresh page loads with long settle waits, at both CSS and device pixel scale — not a one-off render glitch. The underlying DOM text is correct ("Abhi's"), but the computed font-family resolves to "Playfair Display", "Playfair Display Placeholder", serif — that literal "Placeholder" fallback name is the tell. The real webfont isn't binding correctly for this text node's italic-bold style, and whatever it's actually rendering with drops the glyph. This is the single most visible piece of text on the entire site.

homepage hero H1, both branch preview and desktop viewport, 1280×900 and device-scale
Blocked

None of the 7 case-study pages are actually editable — which was the entire point of doing this in Framer

docs/framer-migration.md confirms this itself: every one of the 7 case-study routes was implemented as a route-level React code component dropped into Framer, not native Framer layers. CLAUDE.md's stated goal for this migration is "simple enough for an amateur to edit copy, swap images, and add projects without touching code." As built, Abhi cannot change a single word of case-study copy, swap a single image, or edit a single card without a developer opening the code component. Only the homepage got a native-layer first pass. If this project ships as-is, the client-editability goal — the actual business reason for choosing Framer over just polishing the Next.js site — has not been achieved.

docs/framer-migration.md: "## Recommended Path" + per-route "implemented as a route-level code component" notes
Needs work

The in-page Instagram lightbox — the best feature on the live Next.js site — doesn't exist here

On Social Media Brand Identity, every Instagram link is a plain outbound <a> to instagram.com. There's no lightbox, no in-page overlay, no fetched post data — the feature I'd call the strongest piece of engineering on the Next.js site was dropped somewhere in the migration and never mentioned as a known gap in the build log.

Needs work

Every Next.js bug I found was faithfully copied, not fixed

Confirmed directly: the "One line here" placeholder text on Fully Filmy, the missing Changemaker diary section and matching dead-space gap on Print Media (scroll height is 5691px on both platforms, down to the pixel), and Fun Stuff being completely unreachable on mobile (absent from both the nav dropdown and the mobile Work grid, same as Next.js) all reproduce identically on the Framer branch. The migration was a pixel-for-pixel copy of the current (buggy) state, not an opportunity to fix anything upstream.

Practical implication: fix bugs in the Next.js repo first, then re-sync to Framer — otherwise you're fixing everything twice, once per platform, and they'll drift.

The geometry-matching work in the build log wasn't wasted — it's the functional gaps above that are the problem, not the visual layer.

3. What's actually blocking a client handoff

  • A real resume.pdf from Abhi — everything downstream of this (both platforms' Download Resume button, the Framer placeholder route) is waiting on this one file.
  • A decision: is Framer still the target, or does the Next.js site get polished and shipped on its own? The code-component-everywhere state means Framer currently delivers none of the self-editability that was the reason to choose it. That's a scope conversation with the client, not just an engineering fix.
  • If Framer stays the target: a real contact form (Framer Forms or equivalent), a font-loading fix for the hero headline, and a plan to convert at least the highest-traffic case studies from code components to native layers or Framer CMS entries.
  • Either way: the 8 critical Next.js items in section 1 fixed at the source, then re-synced to Framer if that branch continues.
  • Contact form destination confirmed with the client (still just personal Gmail via mailto on both platforms — fine for now, but worth explicitly confirming it's intentional).

4. Recommended order of operations

  1. Don't trust either platform's self-reported state. Re-verify anything marked "done" in docs/framer-migration.md with a real click-through, the same way this handoff did — that log's screenshot-diff methodology missed the fake contact form and the broken headline entirely.
  2. Fix the 8 critical Next.js items first, in the live repo. It's the source of truth and the faster iteration loop; nothing here needs Framer's build pipeline.
  3. Get the scope decision on Framer before investing more time there — specifically whether code-component case studies are acceptable to the client or whether native/CMS rebuild is required. This changes the remaining effort estimate a lot.
  4. If Framer continues: contact form and the hero font bug are the two functional blockers; re-sync the fixed Next.js content once source-of-truth bugs are resolved, rather than patching both branches in parallel.
  5. Re-run a full responsive pass (phone, all iPad sizes, laptop, up to 4K) on whichever platform ships — the tablet-range clipping bugs found in the Next.js audit are exactly the kind of thing that's easy to reintroduce during any of the above fixes.
